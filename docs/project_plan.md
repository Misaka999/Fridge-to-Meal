# Fridge-to-Meal Agent 项目计划与两人分工

**成员**：Shuhua Zhang、Yangyang Hu  
**课程节点**：11/17 交 Week 6 作业，11/24 项目展示，12/8 交最终代码、Web App 和报告。

项目根据用户现有库存、用餐人数、饮食偏好和到期日，推荐最多三个可做的一餐菜谱，提供用量、步骤和排序理由，并优先使用可安全使用的临期食材。用户更新库存或偏好后，Agent 重新推荐，并保留仍有效的要求。食材不够时说明原因，请用户更新库存信息或调整约束。查询失败、信息不足和确认无可行菜谱是三种不同结果。

## 阶段一 · 11/17 先交可运行的 Week 6 作业

1. **共同约定数据格式。** 每个请求包含 `pantry`、`servings`、`preferences`，有追问时再带上对话和状态。库存至少能记录食材名称、数量、单位和可选的到期日。食谱用稳定的 ID 标识，保存必要食材、用量、份数和步骤。约定三种业务结果：推荐、需要澄清、无可行菜谱；查询失败另有错误状态。每次运行记录模型调用次数、输入和输出 token、耗时与工具调用。先共享一条输入、一条工具返回和一条最终输出样例，双方可据此并行开发。
2. **Shuhua 写最小 ReAct。** 用 proposal 中的 DeepSeek 和 LangGraph，让模型能调用食谱查询工具、读取返回结果、按需追问或给出推荐。先用小型本地食谱表和夹具跑通命令行。单条结果要能用菜谱 ID 或明确的澄清原因判分，工具记录要能定位失败步骤。
3. **Yangyang 写工具、基线和评测入口。** 先用少量人工核对的本地食谱，做食材名称归一、查询和库存匹配。基线用同一模型单次调用，直接读取相同的库存、偏好和候选食谱。脚本从 `tasks.jsonl` 读取用例，通过同一套规则对两种输出评分，保存逐题结果并汇总指标。评分答案和规则留在评测端。
4. **两人各写 25 条，先用 5 条联调。** 50 条覆盖正常推荐、库存与数量、临期排序、偏好或库存变化、缺信息与无解。至少标出 **3 条边界用例**和 **2 条不可回答用例**。边界例可用库存刚够两人份、食材别名和到期字段缺失。不可回答例可用只剩鸡蛋却要求纯素。两人交换审核对方的题，确认库存与预期结果一致。每道独立题开始时重置状态，跨轮测试保留该题自己的会话。
5. **实际运行并打包。** 先跑同样的 50 条 ReAct 与基线对照。再对 ReAct 的每条题独立重跑三次，统计 `pass@3`（至少过一次）和 `pass^3`（三次都过），列出通过与失败交替出现的题。结果表同时给出准确率、平均模型调用次数、平均与 P95 延迟、平均 token。Shuhua 和 Yangyang 一起复核一个失败的调用记录，写一段说明哪一步出了问题、依据是什么、为什么失败。

**11/17 验收**：晚上 11:59 前交 `tasks.jsonl`、评测脚本、含两组对照和重复运行指标的结果表，以及一段失败分析。安全题初稿另备给 Week 7。短期优先跑通真实模型请求、评测和结果保存，网页、完整数据集和第二种 Agent 从下一阶段开始。

## 阶段二 · 11/18–11/23 做完两种 Agent 和展示

1. **补齐共用数据与状态。** Shuhua 实现库存读写、偏好与用餐人数的会话继承。Yangyang 将人工核对的小食谱表扩展为 RecipeNLG 的 `Gathered` 子集，并维护食材别名、份量和单位。只在用量可验证时判定库存充足。参考 FoodKeeper 时，要有相应的储存条件和购买、开封或制备日期；信息不足时请用户补充，或保留未知状态。库存写入只接受用户明确请求或确认。
2. **让两个 Agent 独立使用同一组工具。** Shuhua 让 ReAct 根据每一步工具结果选择下一步。Yangyang 让 plan-and-replan 先产生计划，执行后遇到工具失败、条件变化或无可行选项时按实际状态重新判断。两人分别验证正常、缺信息、无解、查询失败和多轮更新。共用的食材、数量和饮食约束校验由程序执行。
3. **扩充并运行可复现的对照评测。** 两人各增加 75 条功能题，与已有 50 条合并为至少 200 条；另外审核并执行至少 50 条安全题。用同一模型、输入、食谱数据和评分标准比较 ReAct、plan-and-replan、单次 LLM 基线。用程序检查食材、份量、饮食限制、临期排序和更新后的约束，记录模型及工具调用、token、延迟和可取得的成本。安全题检查食谱里的干扰指令是否影响推荐，以及未经确认的库存变更是否被阻止。若结果表中出现不同样本数，注明各自对应的测试集合。
4. **部署并彩排。** Shuhua 验证外部用户可打开网页并连续交互。主场景用 proposal 的两人份素食例子，先展示优先使用明天到期的菠菜，再追加“不要鸡蛋”，检查结果仍保留两人份。第二个场景展示食材不足时的处理。Yangyang 准备设计流程图、测试集构建说明、基线和安全通过率。两人共同录制 3 分钟视频，彩排 2 分钟现场问答。

**11/24 验收**：云端可交互网页、能记住追问的演示、流程图、Agent 与基线结果、至少 50 条安全测试的通过率、3 分钟预录视频和现场问答。Week 6 第 12 页的清单写了 100 个准确率数据点，同页结果表写了至少 200 条；组内按展示前准备至少 200 条来排期。

## 阶段三 · 11/25–12/8 最终交付

1. 两人分别修复各自 Agent 的问题，把可复现的失败加入回归集。每次改动后先跑受影响的题，最终版本再统一重跑功能及安全评测。
2. Shuhua 整理如何配置并启动项目、如何使用网页，以及会话和工具的设计。Yangyang 记录评测命令、模型和数据版本、测试集构成、对照结果和失败类型。两人互相按说明启动并复现一轮样例。
3. 12/7 做组内最终检查。12/8 提交**最终代码、Web App 和报告**，确认报告含 **200+ 条任务**的基准结果和安全结果。
